Developers · Body measurement API

Add 3D body scanning to your product with one API call.

Send a front and a side photo and the person's height. Get their body measurements back, in your own measurement set, and the 3D body as OBJ, glTF or raw geometry if you want it. Typically under 10 seconds.

Overview

Your app captures. We measure. Your system keeps the result.

The scan service is stateless: it builds the 3D body, computes what you asked for, returns it, and keeps nothing. Everything that persists lives on your side.

Quickstart

From two photos to measurements.

One request. Photos go as base64 text inside a JSON body, so it works the same from any language.

  1. Get your API key

    Keys are issued with your agreement, set up for your measurement set, your outputs and your region. Keep server keys in your back end's secret store, never in an app or web page.

  2. Turn each photo into base64

    Use the capture or upload flow your product already has. 1,000–2,000 px on the long side is plenty: photos are scaled to 800 px before measuring, so larger ones only slow the upload.

  3. POST to /v1/measurements

    Send the height and the photos, front first, with your key in the X-API-Key header. Allow up to 120 seconds of client timeout.

  4. Use the result

    Store the measurements against your own record, map them to your size charts, or pass the 3D body to your CAD, pattern or visualization pipeline. Keep the model_version with each result.

import base64, os, requests

API = "https://api.snapmeasureai.com/v1/measurements"
KEY = os.environ["SNAPMEASURE_API_KEY"]   # smk_live_…, kept on your server

def b64(path):
    with open(path, "rb") as f:
        return base64.b64encode(f.read()).decode("ascii")

res = requests.post(API, headers={"X-API-Key": KEY}, timeout=120, json={
    "height": "174cm",                       # or "68.5in"
    "images": [b64("front.jpg"), b64("side.jpg")],
    "include": ["glb"],                      # optional: the 3D body too
    "reference": "order-42",                 # optional: echoed back
})
result = res.json()
if not res.ok:
    err = result["error"]
    raise RuntimeError(f'{err["code"]}: {err["message"]} (request {result["request_id"]})')

print(result["measurements"]["waist circumf"])   # 79.5 (cm)

Authentication

One key per place you call from.

Every request carries an API key in the X-API-Key header (Authorization: Bearer works too). Never put a key in a URL.

Key typePrefixUse it fromProtection
Serversmk_live_Your back endSecret. Refused when sent from a web page. Can be limited to your own IP ranges.
Browsersmk_pub_Your websiteWorks only from the website addresses registered for it, with per-visitor limits.
Appsmk_app_Your mobile appPer-device limits, so one copied key can't run up volume.
  • Rotation without downtime. Hold several keys at once: switch to a new one, then the old one is disabled. Keys can also carry an expiry date.
  • Limits per key. Each key has its own rate limits and number of scans at once, as set in your agreement.
  • Stored as hashes. We keep only a cryptographic hash of each key, so a key is shown once, when it's issued.

Request

Two fields required. Everything else is optional.

A JSON body sent with Content-Type: application/json.

POST/v1/measurements
Photos go inside the JSON, as base64 text

Send each photo's JPEG, PNG or WebP bytes as a base64 string (a data:image/jpeg;base64, prefix is fine), not as a multipart/form-data file. Up to 30 MB and 100 megapixels per photo, 80 MB per request. Phone photos are turned the right way up from their EXIF orientation.

FieldTypeDescription
heightRequiredstring | number"174cm" or "68.5in", or a number with "height_unit": "cm" or "in". The body is scaled to it, so every measurement is at real size.
imagesRequiredarray2–4 photos of one person, front first, then side; a back or second side view helps. Each is a base64 string or {"data": "…"}. Whole body in frame, head to feet.
includeOptionalarrayExtra outputs: obj, glb, geometry, faces, viewer, heights_above_floor, sizes (see Outputs). Without it you get your account's default outputs.
profileOptionalstringYour measurement profile: your own measurement set. Keys with a default profile use it automatically.
unitOptionalstringcm, mm or in. Default: your account's setting, or the height's unit.
poseOptionalstring | objectPose of the 3D files: a_pose (default), t_pose, or your own angles such as {"arms": 45, "legs": 6}. See 3D files.
watertightOptionalbooleantrue: the OBJ and glTF are one closed surface, for cloth simulation, physics and 3D printing.
mesh_unitsOptionalstringOBJ units: m (default), cm or mm. glTF and geometry are always metres.
viewer_styleOptionalstringstudio (every measurement, custom measurements) or showcase (the body large, with the key measurements on it).
referenceOptionalstringYour own identifier, up to 128 characters, returned as sent. We don't store or log it.

No names, emails or account ids are needed. To join a result to your own record, keep your id on your side, or pass it as reference.

Outputs

Measurements, the full 3D body, or both.

Every scan builds a complete 3D body. Take the measurements only, or add any of these, per request or as your account's default.

Body measurements Core

About 20 standard girths and lengths: chest, waist, hips, neck, upper arm, forearm, wrist, thigh, calf, ankle, head, shoulder width, arm length, inseam, torso length, foot length and width. In centimetres, millimetres or inches.

Your measurement set Core

Define any girth or length on the body in the demo's measurement studio (Custom Measure) and save it as a profile. Every scan then returns exactly that set, in your field names, units and rounding.

3D body Core

The body at real size, in the same 10,475-point topology for every scan: OBJ, glTF 2.0 (each measurement as a named line), or raw geometry with named landmarks and joint centres.

Embeddable 3D viewer Optional

A self-contained interactive viewer page for an iframe or web view, in your colours and with your logo or none. It loads nothing from third parties.

Heights above the floor Optional

For each girth, its height above the floor at heel level: the format compression-garment and medical-fit makers specify garments in.

Your size charts Optional

Set up your charts once (one per garment, if you like). Each scan returns the size in each chart, and whether each measurement sits below, within or above it.

Person check Built in

Every photo is checked for a person before it is measured. Photos without one are left out and listed in photos.unused, so your app can ask for that photo again; with fewer than two usable photos the answer is 422 no_person_detected.

Measurement definitions are our own, written out in the catalog; they are not certified to a published standard such as ISO 8559-1. A measurement profile can add measurements to any standard's definitions.

3D files

The same body, in the pose your pipeline needs.

Measurements are always taken in the same pose, so these options change only the 3D files (obj, glb, geometry), never the numbers.

OptionValuesUse it for
posea_pose (default, also called measure): arms about 66° below horizontal, the pose measurements are taken inComparing scans, a natural standing body
poset_pose: arms level, legs straightGame engines, avatars, auto-rigging tools
pose{"arms": 45, "legs": 6}: arms 0–70° below horizontal, each leg 0–20° outCloth simulation, matching the avatar your garments were made on
watertighttrue: one closed surfaceCloth collision, physics, volume, 3D printing
mesh_unitsm, cm, mm (OBJ)CAD and cloth tools that expect cm or mm

One topology for every scan

Every body has the same 10,475 vertices in the same order and the same triangles, whatever the person's shape. Vertex i is the same point on the body in every scan, so two scans of a person compare point by point with no extra processing.

Coordinates

  • Metres; +y is up and the body faces +z (its left side at +x).
  • The floor is at y = 0 and the origin is between the heels.
  • Geometry arrays are little-endian base64 (float32 vertices, uint16 faces).
  • No skeleton or skinning weights: rig the watertight A-pose or T-pose body in your own tool; geometry.joints gives the joint centres.

Limits & retries

Built for production traffic.

Rate-limit headers

Every response carries the standard headers for your key's per-minute limit, and errors that ask you to wait carry Retry-After.

X-Request-Id:        3f9a1c0d2b7e4a51
RateLimit-Limit:     120
RateLimit-Remaining: 117
RateLimit-Reset:     42

Client guidance

  • Retry safely. Retry 429 and 503 after Retry-After seconds, and 500 once. A scan changes nothing on our side, so a retry never double-counts state.
  • Pace concurrency. Send a few scans at once per key (your agreement says how many) and queue the rest; each takes a few seconds.
  • Time out at 120 seconds. Uploads must finish within 60.
  • Quote the request id. It's in every response, header and body, and is all we need to look into a request.
  • Check readiness with GET /health, which needs no key.

Security & data handling

Built so there's nothing to leak.

The simplest way to protect body photos is never to keep them. Here is what happens to the data in a scan, end to end.

Photos are never stored

Photos and heights are processed in memory, on a read-only file system, and deleted as soon as the response is sent. They are never written to disk, logged or used for training.

No personal data in logs

Logs record technical details only (status, duration, error type), never photos, heights, measurements or IP addresses, and are deleted within days. We count scans per customer for billing: counts only.

Encrypted and filtered

TLS 1.2 or higher on every connection, a web application firewall in front of the service, API keys stored only as hashes, and per-key and per-visitor rate limits.

Ready for your review

A Data Processing Agreement, a security overview for your IT review, and a dedicated instance with private networking when your policies need it. The 3D viewer contacts no third parties.

Versioning

Stable to build on.

  • /v1 is stable. Anything that would break an integration comes with a new version path and advance notice, as set out in your agreement.
  • Additions arrive without notice. New optional fields and outputs can appear at any time, so ignore fields you don't recognise.
  • model_version changes only when the measurement models change. Store it with each result, so you know which model measured it.
  • Existing integrations on the original POST /body/analyze contract keep working; new integrations should use /v1/measurements.

FAQ

Developer questions

Which languages and platforms are supported?

Anything that can make an HTTPS request with a JSON body: any back-end language, web, iOS or Android. There is no SDK to install; the OpenAPI 3.1 file imports into Postman and generates a typed client for most languages.

Can we call the API from our website or mobile app?

Yes. Browser keys work only from the website addresses registered for them, and app keys carry per-device limits. Server keys stay on your back end: requests made with a server key from a web page are refused.

How can we try it before signing?

The live demo runs the same scan, free, in any browser, including the measurement studio for defining your own measurements. API keys are issued with an agreement and set up for your use case: your measurement set, your outputs and your region.

Can we get only the measurements, or only the 3D body?

Yes. Choose per request with include, or set your account's default outputs. Many integrations take the measurements for sizing and the OBJ or glTF body for their pattern, CAD or visualization tools.

How do we define our own measurements?

Open the measurement studio on a demo result, use Custom Measure to define any girth or length on the body, and save it as a measurement profile. We attach it to your keys, and every scan returns exactly that set, with your field names, units and rounding.

Are photos or results stored?

No. Photos and heights are processed in memory and deleted as soon as the response is sent. They are never written to disk, logged or used for training, and results go back to your system rather than being kept by SnapMeasureAI.

How fast is a scan?

Processing takes about five seconds; the upload adds to that, so send photos of 1,000–2,000 px on the long side. When many scans arrive at once, capacity is added automatically, and a busy answer tells you when to retry.

Will the API change under us?

No. /v1 is stable. New optional fields and outputs can be added at any time, so ignore fields you don't recognise. A change that would break an integration comes with a new version path and advance notice, as set out in your agreement.
