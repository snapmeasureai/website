Overview

Your app captures. We measure. Your system keeps the result.

The scan service is stateless: it builds the 3D body, computes what you asked for, returns it, and keeps nothing. Everything that persists lives on your side.

Your app or website

Capture

Your user takes a front and a side photo and enters their height, in your own capture screen or with our capture SDK inside your page.

  • Any smartphone camera
  • Everyday clothes work
HTTPS · JSON

SnapMeasureAI · stateless

Reconstruct & measure

The person is found in every photo, the views are combined into one 3D body at the real height, and your measurements are taken on it.

  • Processed in memory
  • Photos never written to disk

Your system

Store & use

Measurements and the 3D body land in your system, joined to your own user, order or patient record, under your retention policy.

  • You hold the history
  • Size charts, CAD, progress views

Typically 5–7 seconds from photos to result, nearly all of it processing: the prepared photos are a few hundred kilobytes.

Quickstart

From two photos to measurements.

One request. Photos go as base64 text inside a JSON body, so it works the same from any language.

  1. Get your API key

    Keys are issued with your agreement, set up for your measurement set, your outputs and your region. Keep server keys in your back end's secret store, never in an app or web page.

  2. Turn each photo into base64

    Use the capture or upload flow your product already has. 1,000–2,000 px on the long side is plenty: photos are scaled to 800 px before measuring, so larger ones only slow the upload.

  3. POST to /v1/measurements

    Send the height and the photos, front first, with your key in the X-API-Key header. Allow up to 120 seconds of client timeout.

  4. Use the result

    Store the measurements against your own record, map them to your size charts, or pass the 3D body to your CAD, pattern or visualization pipeline. Keep the model_version with each result.

import base64, os, requests

API = "https://api.snapmeasureai.com/v1/measurements"
KEY = os.environ["SNAPMEASURE_API_KEY"]   # smk_live_…, kept on your server

def b64(path):
    with open(path, "rb") as f:
        return base64.b64encode(f.read()).decode("ascii")

res = requests.post(API, headers={"X-API-Key": KEY}, timeout=120, json={
    "height": "174cm",                       # or "68.5in"
    "images": [b64("front.jpg"), b64("side.jpg")],
    "include": ["glb"],                      # optional: the 3D body too
    "reference": "order-42",                 # optional: echoed back
})
result = res.json()
if not res.ok:
    err = result["error"]
    raise RuntimeError(f'{err["code"]}: {err["message"]} (request {result["request_id"]})')

print(result["measurements"]["waist circumf"])   # 79.5 (cm)
import { readFile } from "node:fs/promises";

const API = "https://api.snapmeasureai.com/v1/measurements";
const KEY = process.env.SNAPMEASURE_API_KEY;   // smk_live_…, kept on your server
const b64 = async (path) => (await readFile(path)).toString("base64");

const res = await fetch(API, {
  method: "POST",
  headers: { "Content-Type": "application/json", "X-API-Key": KEY },
  body: JSON.stringify({
    height: "174cm",                             // or "68.5in"
    images: [await b64("front.jpg"), await b64("side.jpg")],
    include: ["glb"],                            // optional: the 3D body too
    reference: "order-42",                       // optional: echoed back
  }),
  signal: AbortSignal.timeout(120_000),
});
const result = await res.json();
if (!res.ok) {
  const { code, message } = result.error;
  throw new Error(`${code}: ${message} (request ${result.request_id})`);
}

console.log(result.measurements["waist circumf"]);   // 79.5 (cm)
# Base64-encode each photo onto one line, then build the JSON body
FRONT=$(base64 < front.jpg | tr -d '\n')
SIDE=$(base64 < side.jpg | tr -d '\n')
printf '{"height":"174cm","images":["%s","%s"]}' "$FRONT" "$SIDE" > scan.json

curl https://api.snapmeasureai.com/v1/measurements \
  -H "X-API-Key: $SNAPMEASURE_API_KEY" \
  -H "Content-Type: application/json" \
  --max-time 120 \
  -d @scan.json

Capture SDK

The guided camera, inside your own page.

Add one script and call SnapMeasure.capture(). The guided camera flow runs on your domain and in your design, sends the photos straight to the API with your browser key, and hands the result to your page's code.

  1. Add the script

    From the API's own domain, pinned to its version with an integrity hash, or bundled from npm (@snapmeasureai/capture) so no third-party script runs on your page.

  2. Call capture() when your user is ready

    Pass the height if your form already asks for it; otherwise the SDK asks. Add include: ["weight"] and you can drop the weight question too.

  3. Take it from there

    The promise resolves with the same JSON as /v1/measurements, the SDK closes, and your next step shows. Closing it rejects with cancelled.

  4. Choose where your key lives

    A browser key is public by design: anyone can read it in your page's source. It only runs scans, only from your registered websites, within per-visitor limits and your monthly cap, and there's no stored data for it to reach. To keep any key out of the page, use proxyUrl: "/api/body-scan" instead of apiKey: a route on your own server that adds your server key and forwards the request. This also suits store tablets that share one internet connection.

your page 
<script src="https://api.snapmeasureai.com/sdk/capture-1.0.0.js"
        integrity="sha384-QECijm30jZtgcqPgpWhWi+37FumYQJbFRr470rQEiVaPd+qmccgpQSqbT+5ooLP+"
        crossorigin="anonymous"></script>
<script>
  button.onclick = async () => {
    try {
      const scan = await SnapMeasure.capture({
        apiKey: "smk_pub_…",          // public, works only on your website (step 4)
        // proxyUrl: "/api/body-scan", // or no key: your server adds it
        height: form.height.value,      // or leave out: the SDK asks
        include: ["weight"],
        theme: { accent: "#1D1D1B", font: "Your Sans, sans-serif" },
      });
      nextStep(scan.measurements, scan.weight);
    } catch (err) {
      if (err.code !== "cancelled") showRetry(err.code);
    }
  };
</script>

Built in

Guidance and recovery

The whole picture inside a frame in your colour, instructions never over the person, photo review and retake, upload without a camera, automatic retries.

Private

Nothing left behind

No cookies, storage or third parties. Photos are re-encoded on the device, without location data, and the camera turns off the moment it closes.

Phones, tablets and computers, in current Safari, Chrome, Edge, Firefox and Samsung Internet, on HTTPS pages. About 27 KB gzipped, no dependencies, TypeScript types included. Two people in one visit: call capture() once for each.

What your customer sees

  1. Start. Three setup steps (prop the phone up, stand 2–3 m back, no coats or baggy layers with arms slightly out), the height field if you didn't pass a height (in ft/in on US pages, cm elsewhere), a privacy line or your consent checkbox, then Start or Upload photos instead. One screen before the camera.
  2. Camera. The whole camera picture, never cropped, inside a border in your colour: the person stands inside the frame. Instructions, the countdown and the buttons sit in a panel below the picture, or beside it on wide screens, never over the person. Self-capture: Start countdown, a 10-second countdown as one large number with a cue readable from 2–3 m and beeps in the last three seconds, then Turn to your side in large type (the frame turns amber) and a 7-second side countdown that starts on its own. Nothing on the camera screen is animated, so it behaves the same on every device. Stop returns to the start without leaving. Assisted: a shutter button.
  3. Check the photos. Both photos, each with Retake, and Retake both. On phones they sit one above the other, as large as fits, with no scrolling.
  4. Measuring. The front photo with a scan line and the three stages, a few seconds. Busy moments are retried on their own.
  5. Done. The SDK closes and your page has the result, for your own results page or next step. (showResult: true shows a short summary first.)

Camera blocked, or none: two upload tiles instead. No whole body found: the SDK explains and offers to retake. Height out of range: it asks again and resends the same photos.

Results and errors

The promise resolves with the API's response, unchanged: the same JSON as /v1/measurements, with weight and uncertainty when you include them. It rejects with a SnapMeasure.Error (code, status, requestId, retryAfter, retryable). By then the customer has already seen a clear message and a way forward; the code is for your page and your logs.

codeMeaning
cancelledThe customer closed it, or your code did.
camera_denied, camera_unavailableCamera blocked or failing, and they closed instead of uploading.
no_person_detected, invalid_imageThey closed after being asked to retake.
network, timeout, busyConnection trouble, after the automatic retries.
rate_limited, monthly_limit_reachedYour key's limits.
invalid_config, origin_not_allowed, invalid_api_key, …Setup problems only you can fix. Also written to the browser console.

Methods and requirements

  • capture(options) the guided flow, resolving with the result.
  • measure(options) no interface: pass images you captured yourself (File, Blob, image, video, canvas or base64). It resizes them, strips their metadata, sends them with the same retries and resolves with the same result.
  • isSupported() {camera, upload, secureContext, fetch}, to decide whether to show your button.
  • close(), parseHeight(value, unit), version, Error.
  • HTTPS. Browsers allow the camera only on secure pages. In an iframe, add allow="camera".
  • Content-Security-Policy. Allow https://api.snapmeasureai.com in script-src (unless you bundle it) and connect-src, and blob: data: in img-src. No eval, inline scripts or 'unsafe-inline' needed.
  • Accessible. A labelled dialog that keeps focus inside, fully keyboard operable, every control named for screen readers, progress announced, no animation for users who ask for reduced motion.
  • Versions. capture-1.0.0.js is the current version; pin it with integrity.

Authentication

One key per place you call from.

Every request carries an API key in the X-API-Key header (Authorization: Bearer works too). Never put a key in a URL.

Key typePrefixUse it fromProtection
Serversmk_live_Your back endSecret. Refused when sent from a web page. Can be limited to your own IP ranges.
Browsersmk_pub_Your websitePublic by design: visible in your page's source, but it only runs scans, only from the website addresses registered for it, with per-visitor limits.
Appsmk_app_Your mobile appPer-device limits, so one copied key can't run up volume.
  • No key in the browser, if you prefer. Your website can send scans through your own server, which adds your server key. The capture SDK supports this with its proxyUrl option.
  • Rotation without downtime. Hold several keys at once: switch to a new one, then the old one is disabled. Keys can also carry an expiry date.
  • Limits per key. Each key has its own rate limits and number of scans at once, as set in your agreement.
  • Stored as hashes. We keep only a cryptographic hash of each key, so a key is shown once, when it's issued.

Request

Two fields required. Everything else is optional.

A JSON body sent with Content-Type: application/json.

POST/v1/measurements
Photos go inside the JSON, as base64 text

Send each photo's JPEG, PNG or WebP bytes as a base64 string (a data:image/jpeg;base64, prefix is fine), not as a multipart/form-data file. Up to 30 MB and 100 megapixels per photo, 80 MB per request. Phone photos are turned the right way up from their EXIF orientation.

FieldTypeDescription
heightRequiredstring | number"174cm" or "68.5in", or a number with "height_unit": "cm" or "in". The body is scaled to it, so every measurement is at real size.
imagesRequiredarray2–4 photos of one person, front first, then side; a back or second side view helps. Each is a base64 string or {"data": "…"}. Whole body in frame, head to feet.
includeOptionalarrayExtra outputs: weight, uncertainty, obj, glb, geometry, faces, viewer, heights_above_floor, sizes (see Outputs). Without it you get your account's default outputs.
profileOptionalstringYour measurement set, built in the measurement builder. Keys with a default set use it automatically.
unitOptionalstringcm, mm or in. Default: your account's setting, or the height's unit.
weight_unitOptionalstringkg or lb, for the estimated weight. Default: lb when the measurements are in inches, otherwise kg.
poseOptionalstring | objectPose of the 3D files: a_pose (default), t_pose, or your own angles such as {"arms": 45, "legs": 6}. See 3D files.
watertightOptionalbooleantrue: the OBJ and glTF are one closed surface, for cloth simulation, physics and 3D printing.
mesh_unitsOptionalstringOBJ units: m (default), cm or mm. glTF and geometry are always metres.
viewer_styleOptionalstringstudio (every measurement, custom measurements) or showcase (the body large, with the key measurements on it).
referenceOptionalstringYour own identifier, up to 128 characters, returned as sent. We don't store or log it.

No names, emails or account ids are needed. To join a result to your own record, keep your id on your side, or pass it as reference.

Outputs

Measurements, the full 3D body, or both.

Every scan builds a complete 3D body. Take the measurements only, or add any of these, per request or as your account's default.

Body measurements Core

18 standard girths and lengths: chest, waist, hips, neck, upper arm, forearm, wrist, thigh, calf, ankle, head, shoulder width, back to shoulder, arm length, inseam, torso length, foot length and width. In centimetres, millimetres or inches. Add your own in the measurement builder.

Your measurement set Core

Define any girth or length on the body in the demo's measurement studio (Custom Measure) and save it as a profile. Every scan then returns exactly that set, in your field names, units and rounding.

3D body Core

The body at real size, in the same topology for every scan: OBJ, glTF 2.0 (each measurement as a named line), or raw geometry with named landmarks and joint centres.

Embeddable 3D viewer Optional

A self-contained interactive viewer page for an iframe or web view, in your colours and with your logo or none. It loads nothing from third parties.

Heights above the floor Optional

For each girth, its height above the floor at heel level: the format compression-garment and medical-fit makers specify garments in.

Your size charts Optional

Set up your charts once (one per garment, if you like). Each scan returns the size in each chart, and whether each measurement sits below, within or above it.

Estimated weight Optional

The body weight estimated from the scan's height and girths, with a 90% range, so your users needn't type it in. Fitted on public surveys in which people were both tape-measured and weighed (NHANES and ANSUR II, over 33,000 adults). No extra input needed. An estimate for recommendations, not a weighing.

Measurement uncertainty Optional

For every measurement, a range the true value falls inside 9 times in 10, such as waist 79.5 cm, likely 72.8–86.2. Calibrated on how far our measurements actually were from 3D-scanned and tape-measured people, not on the model's own confidence. Use it to show a range, flag a body between two sizes, or ask for a tape check where it matters.

Person check Built in

Every photo is checked for a person before it is measured. Photos without one are left out and listed in photos.unused, so your app can ask for that photo again; with fewer than two usable photos the answer is 422 no_person_detected.

3D files

The same body, in the pose your pipeline needs.

Measurements are always taken in the same pose, so these options change only the 3D files (obj, glb, geometry), never the numbers.

One topology for every scan

Every body has the same vertices in the same order and the same triangles, whatever the person's shape. Vertex i is the same point on the body in every scan, so two scans of a person compare point by point with no extra processing.

Coordinates

  • Metres; +y is up and the body faces +z (its left side at +x).
  • The floor is at y = 0 and the origin is between the heels.
  • Geometry arrays are little-endian base64 (float32 vertices, uint16 faces).
  • No skeleton or skinning weights: rig the watertight A-pose or T-pose body in your own tool; geometry.joints gives the joint centres.

Limits & retries

Built for production traffic.

Rate-limit headers

Every response carries the standard headers for your key's per-minute limit, and errors that ask you to wait carry Retry-After.

X-Request-Id:        3f9a1c0d2b7e4a51
RateLimit-Limit:     120
RateLimit-Remaining: 117
RateLimit-Reset:     42

Plans with a monthly number of scans also carry X-Scans-Limit, X-Scans-Remaining and X-Scans-Renew. Only measured scans count, and the month runs from the day your key was issued.

Client guidance

  • Retry safely. Retry 429 and 503 after Retry-After seconds, and 500 once. A scan changes nothing on our side, so a retry never double-counts state.
  • Pace concurrency. Send a few scans at once per key (your agreement says how many) and queue the rest; each takes a few seconds.
  • Time out at 120 seconds. Uploads must finish within 60.
  • Quote the request id. It's in every response, header and body, and is all we need to look into a request.
  • Check readiness with GET /health, which needs no key.

Security & data handling

Built so there's nothing to leak.

The simplest way to protect body photos is never to keep them. Here is what happens to the data in a scan, end to end.

Photos are never stored

Photos and heights are processed in memory, on a read-only file system, and deleted as soon as the response is sent. They are never written to disk, logged or used for training.

No personal data in logs

Photos, heights, measurements and IP addresses are never written to logs, not even briefly. Logs hold only technical details (status, duration, error type) and are kept for a short time for troubleshooting. For billing we keep a count of scans per customer, and nothing else.

Encrypted and filtered

TLS 1.2 or higher on every connection, a web application firewall in front of the service, API keys stored only as hashes, and per-key and per-visitor rate limits.

FAQ

Developer questions

Which languages and platforms are supported?

Anything that can make an HTTPS request with a JSON body: any back-end language, web, iOS or Android. For websites there is the capture SDK, one script with the whole guided camera flow; for everything else, the OpenAPI 3.1 file imports into Postman and generates a typed client for most languages.

Can the scan give the person's weight?

Yes, as an estimate: add "weight" to include. It is computed from the scan's height and girths with formulas fitted on public survey data (NHANES and ANSUR II) and comes with a 90% range. From tape measurements the formulas are within about 2% on average; from photos, the error of the photo measurements adds to that. It is meant for recommendations, not for medical use.

Can two people be measured in one visit?

Yes, one after the other: each scan is one person, with their own height and their own result. With the SDK, call capture() once for each.

Can we call the API from our website or mobile app?

Yes. Browser keys work only from the website addresses registered for them, and app keys carry per-device limits. Server keys stay on your back end: requests made with a server key from a web page are refused.

How can we try it before signing?

The live demo runs the same scan, free, in any browser, including the measurement studio for defining your own measurements. API keys are issued with an agreement and set up for your use case: your measurement set, your outputs and your region.

Can we get only the measurements, or only the 3D body?

Yes. Choose per request with include, or set your account's default outputs. Many integrations take the measurements for sizing and the OBJ or glTF body for their pattern, CAD or visualization tools.

How do we define our own measurements?

Open our measurement builder (a default 3D body, no scan needed), use Custom Measure to define any girth or length on the body, and save it as a measurement set. We attach it to your keys, and every scan returns exactly that set, with your field names, units and rounding.

Are photos or results stored?

No. Photos and heights are processed in memory and deleted as soon as the response is sent. They are never written to disk, logged or used for training, and results go back to your system rather than being kept by SnapMeasureAI.

How fast is a scan?

Processing takes about five seconds; the upload adds to that, so send photos of 1,000–2,000 px on the long side. When many scans arrive at once, capacity is added automatically, and a busy answer tells you when to retry.

Will the API change under us?

No. /v1 is stable. New optional fields and outputs can be added at any time, so ignore fields you don't recognise. A change that would break an integration comes with a new version path and advance notice, as set out in your agreement.
